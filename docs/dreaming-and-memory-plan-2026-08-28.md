## 一、这份文档要解决什么

一期把长期记忆的**存取机制**做完了：独立库、画像/事实两层、注入预算、打分检索。
但记忆里**装什么**几乎完全依赖模型在对话中主动调 `remember`，覆盖率低且偏随机。

二期要补的是**内容供给**：让系统在离线时段主动从用户已有的笔记里归纳出高价值的
长期结论，写进记忆，并让每日提示这类高频触点真正用上它。

## 二、现状核查（2026-08-28，带 file:line）

### 1. 注入管道已经全线打通，不需要新建

| 消费方 | 注入点 | 状态 |
|---|---|---|
| Thoughter 对话 | `agent_service.dart:319` | ✅ 已注入画像 |
| 每日提示 | `ai_service.dart:639` → `652` | ✅ 已注入画像 |
| 周期洞察 | `ai_service.dart:472` → `503` | ✅ 已注入画像 |
| 空周期洞察 | `ai_service.dart:533` → `547` | ✅ 已注入画像 |

统一入口是 `AIService._userProfileContext()`（`ai_service.dart:47`），内部走
`AgentMemoryService.safeProfileBlock`。`ai_service.dart:36` 的注释已经写明
"每日提示与周期洞察共用 Thoughter 的同一份记忆"。

**结论：二期不需要碰注入侧。** "让每日提示提起用户近况"这件事，缺的不是管道，
是画像层里根本没有这类内容。

### 2. 画像层装不下"近况"，是模型定义决定的

`AgentMemoryKind`（`agent_memory.dart:8-20`）只有四类：`identity` / `preference` /
`style` / `feedback`。枚举上方的注释把边界写死为"只覆盖**从笔记内容里推导不出来**的
信息"——而"最近在做什么、去了哪里"恰恰是从笔记里推导出来的，按现行规则进不了记忆。

### 3. 注入预算是硬约束

`profileInjectionMaxEntries = 24`、`profileInjectionMaxChars = 1200`
（`agent_memory_service.dart:61-62`）。**画像层是零和的**：多写一条低价值的，就会挤掉
一条高价值的。这一条决定了二期不能是"多记一点"，必须是"记得更准"。

### 4. 会话检索存在，但没暴露给模型

`ChatSessionService.searchSessions()`（`chat_session_service.dart:670`）已实现，
但唯一调用方是历史页 UI（`session_history_page.dart:131`）。已注册的 agent 工具见
`app_providers.dart:48-61`，其中没有会话检索。**模型目前无法回答"我们上次聊过什么"。**

### 5. 记忆与会话都不进备份、不跨设备

`backup_service.dart` 与 `webdav_sync_service.dart` 均未引用 `agent_memory.db` 或
会话库。换设备即失忆。这是一期的显式取舍，见第八节待办。

## 三、产品判断：记忆在**笔记应用**里该是什么

这一节是本方案的依据，实现细节都从这里推出来。

### 3.1 记忆是缓存，不是档案

通用助手的记忆解决的是"从零认识你"。笔记应用不存在这个问题——**用户的笔记本身
就是最完整的自我记录**，而且模型随时能用 `explore_notes` 读到。

所以记忆在这里的价值不是"知道更多"，而是"**不必每次重新读一遍**"。它是一层缓存。
这个 framing 直接给出可判定的准入标准，**三个条件必须同时满足**：

| 条件 | 含义 | 反例 |
|---|---|---|
| **归纳成本高** | 要扫很多篇笔记才得出 | "用户上周写了三条" —— 一次检索就有 |
| **结论稳定** | 数月尺度上不变 | "用户最近在准备某场考试" —— 几周后失效 |
| **复用频率高** | 多数次交互都用得上 | "用户 2023 年用过某个标签" —— 几乎不会再用 |

按这个标准：**文风该记**（扫一个月才归纳得出、数月不变、每次代笔都要用）；
**近况不该进画像层**（成本低、会过期）——但它对每日提示确实有价值，所以另设带
过期时间的通道，见 4.3。

> 这条标准取代了一期注释里的"从笔记里推导不出来的才进记忆"。旧表述把
> **原始内容**和**派生结论**混为一谈了：文风、品味、近况都是从笔记*归纳*出来的
> 结论，不是笔记内容本身。归纳很贵、结论很短，正是该缓存的东西。
> 真正要守住的边界是：**记忆存结论，不存原文**。要原文永远去 `explore_notes`。

### 3.2 最大的失败模式不是记不住，是记错了还改不掉

用户看到助手说"你习惯写短句"而他并不是——这比什么都不记**伤害更大**。因为它同时
暴露了两件事：系统在背地里给他建模，且建错了。

由此得到两条硬性要求，写在第七节前置条件里：

- **可见**：用户必须能看到系统记了什么，并能删。
- **可归因**：dreaming 写入的每条记忆都要能说清依据来自哪几篇笔记。

**静默 ≠ 不透明。** 用户要的"静默保存"指的是*不打断*，不是*不可查*。二期必须
同时满足这两点；只做前者是在积累信任债。

### 3.3 摘录与原创必须分开建模

这是 ThoughtEcho 区别于通用笔记应用的地方：笔记有 `excerpt`（摘抄他人）和
`original`（用户原创）之分，`explore_notes` 已经在返回这个字段。落到记忆上：

- **摘录反映他向往的**，原创反映**他实际的**。
- 二者常常不一致：爱摘凝练的古文、自己写口语化的碎句，是很正常的组合。

**如果混成一类记忆，助手代笔时会照着他摘的东西写，产出完全不像他。** 这是本方案
坚持拆成两类记忆（`taste` / `voice`）的唯一理由，不是分类洁癖。

同时立一条**内容约束**：`taste` 类记忆只能用于**共鸣与推荐**，
绝不能用于**评价**。系统不得生成任何比较用户"摘的"与"写的"之间落差的表述。
这类话即使准确也具有冒犯性，且用户从未请求过这种评价。

**这条约束必须在注入层执行，不能只写在提示词里。** 光靠提示词约束等于没有约束——
条目一旦进了画像块，任何生成路径都能拿它去做任何事。执行方式是**按消费方做 kind 投影**：

| 消费方 | 注入哪些 kind | 理由 |
|---|---|---|
| 每日提示 | `identity` / `style` / `voice` + 近况切片 | 它只写一两句话，不做推荐，`taste` 对它无用；不注入即无法误用 |
| 周期洞察 | `identity` / `style` / `voice` + 近况切片 | 同上，且洞察本身最接近"评价"，更要隔离 `taste` |
| Thoughter 对话 | 全部 | 唯一需要 `taste` 的场景（共鸣、推荐），并由提示词补充禁止评价 |

即：`taste` **在物理上到不了**洞察与每日提示这两条最可能产生评价口吻的路径。
提示词约束只作为对话路径的第二道防线。

### 3.4 每日提示的注入应比对话更保守

每日提示是用户每天第一眼看到的内容。注入记忆能让它从通用文案变成"像是认识他的
一句话"，但**风险是对称放大的**：每天出现的东西，说错一次的印象成本远高于对话里
说错一次——对话里用户可以立刻反驳，每日提示他只能沉默地看着。

因此每日提示只消费**高置信度**条目与**未过期**的近况切片，不消费事实层。

### 3.5 挂在周期洞察之后，是产品决策

用户点开周期洞察时，本来就处在"回顾最近的自己"的心态里。系统在同一刻做同一件事，
是同频的；而且笔记集合刚被读过、周期边界现成、用户已为这批笔记付过一次模型调用，
**边际成本最低**。

对比 OpenClaw 的凌晨 cron：在移动端还要额外处理后台唤醒限制与电量策略，
收益却不比"跟着洞察走"更高。周/月一次的频率对文风这类稳定结论也完全够用。

### 3.6 失败静默，收益隐性

- **失败**：不提示、不重试、不留痕给用户，下个周期自然重来。dreaming 是增益，
  任何情况下都不能让用户感到"有个后台任务坏了"。
- **成功**：也不要弹"已为你提炼 N 条记忆"。那是把系统成本暴露给用户。
  收益应当只体现在后续回应的质量上。

## 四、设计

### 4.1 扩展 `AgentMemoryKind`

在现有四类之外新增两类：

| 新增 | 装什么 | 与哪个易混 | 示例（示意，非真实用户数据） |
|---|---|---|---|
| `taste` | 摘录品味：常摘的类型、题材、调性 | ≠ `preference`（想聊什么话题） | "摘录以哲学随笔和诗歌为主，偏好凝练的短句" |
| `voice` | 用户自己的写作声音：篇幅、句式、人称、收尾方式 | ≠ `style`（希望助手怎么表达） | "原创笔记多为 50–120 字的第一人称碎句，少用书面连接词" |

`preference` 与 `style` 的既有语义不变。两组的区分见 3.3。

### 4.2 事实层保持不变

`taste` / `voice` 都是画像层条目（稳定、需常驻）。事实层仍只接受
`remember` 写入的细节，dreaming 只做**去重**与**晋升**，不新增事实。

### 4.3 近况切片（新增，独立于画像层）

近况**不进画像层**（理由见 3.1）。单独一张表：

- 一次 dreaming 只产出**一条**切片，覆盖式写入（不追加）。
- 带 `expires_at`，**默认 14 天**；过期即不注入，无需清理任务。
- 内容限定在：最近在做的事、去过的地方、反复提到的主题。**不含情绪判断**。
- 长度上限约 200 字，不占用画像层的 24 条 / 1200 字预算。

> 14 天是初值，需要在一期数据上校准。取值依据：周报周期是 7 天，14 天能跨过
> 一个"用户这周没写"的空窗而不至于让内容陈旧到出错。

### 4.4 Dreaming 流程

**触发**：`InsightHistoryService.addInsight()`（`insight_history_service.dart:90`）
成功落库之后，起一个不阻塞 UI 的后台任务。

> **不要挂在 `AIService.generateInsights`（`ai_service.dart:679`）上。** 该方法在
> `lib/` 与 `test/` 中**零调用方**，是历史遗留的死代码；真实的周期洞察走
> `streamReportInsight` / `streamEmptyPeriodInsight`
> （`explore_data_loading.dart:379`、`534`）。挂在它上面 dreaming 永远不会触发。
>
> 也不挂在 `explore_data_loading.dart` 的 `onDone` 上：那是页面 State，
> dreaming 不该由某个页面的生命周期驱动。`addInsight` 是正确的层——它是服务，
> 内部已过滤 `isAiGenerated`（本地兜底文案不触发 dreaming，因为那时模型根本没跑），
> 且每次成功落库恰好触发一次。

**前置门槛**（任一不满足则整轮跳过，不重试）：

1. 用户已开启长期记忆（`SettingsService.agentMemoryEnabled`）；
2. 本周期笔记数达到最低样本量（初值 10 条，样本太少归纳不出稳定结论）；
3. 距上次成功 dreaming 已超过最小间隔（初值 7 天，防止用户反复点开洞察触发多轮）；
4. AI 配置可用。

**阶段**：

| 阶段 | 做什么 | 用不用模型 |
|---|---|---|
| A. 采样 | 按周期取笔记，按 `excerpt` / `original` 分两组，各自取样 | 否 |
| B. 归纳 | 两组分别归纳出 `taste` / `voice` 候选；另归纳一条近况切片 | 是（便宜档） |
| C. 校验 | 长度、条数、格式校验；与现有画像去重；候选带来源笔记 id | 否 |
| D. 写入 | 通过校验的走 `update`（同 kind 原位更新），不追加 | 否 |

**关键约束**：

- **同 kind 原位更新，绝不追加**。`voice` 永远只有一条。追加会在画像层里堆出
  一串互相矛盾的文风描述，并挤掉其它条目（预算是零和的，见 2.3）。
- **B 阶段任何异常一律整轮放弃**，保留原有记忆。宁可不更新，不可写坏。
- **候选必须带来源笔记 id**，用于 3.2 的可归因要求。存储方式见 4.4.1——
  现有写入接口的 `source` 只是个自由字符串（默认 `thoughter`），存不住结构化来源，
  必须新增字段并迁移，否则"可归因"这条前置无法落地。
- 归纳只读笔记的**结构与语言特征**，不复述具体私人内容——写进画像的应是
  "多为 50–120 字的第一人称碎句"，而不是任何一条笔记的实际内容。

### 4.4.1 来源归因的存储与迁移

记忆库 schema 从 `1` 升到 `2`（`AgentMemoryService.schemaVersion`）。

- 画像表新增 `source_note_ids TEXT`，存 JSON 字符串数组（如 `["id-a","id-b"]`）。
  选 JSON 列而不是关联表：一条画像的来源就几篇，关联表要多一次 join
  和一套级联删除，收益不抵复杂度。
- **旧条目与用户/模型手动写入的条目该列为 NULL**，语义是"无来源"，
  管理列表按无来源展示，不阻塞读取、更新或删除。
- `remember` 工具写入路径不填该列——只有 dreaming 填。手动记下的东西没有笔记来源，
  硬造一个反而是假归因。
- 建表语句沿用一期的 `IF NOT EXISTS` + `onUpgrade` / `onOpen` 都跑一遍的自愈策略；
  加列用 `ALTER TABLE ... ADD COLUMN` 并吞掉"列已存在"错误。

近况切片单独建表 `agent_memory_recent_slice`，同一迁移里创建：单行覆盖式写入
（固定主键），字段为内容、`expires_at`、`source_note_ids`、观察时间。

### 4.5 每日提示消费侧

`_userProfileContext()` 之外再取一块未过期的近况切片，拼进同一个 user 消息。
切片缺失或过期时按现状工作——**记忆是增益，不是前置条件**
（沿用 `ai_service.dart:39` 已确立的原则）。

画像块的渲染逻辑需要一处改动：按 3.3 的 kind 投影表接受一个 kind 白名单，
`AIService` 的四条路径传"不含 `taste`"的集合，`AgentService` 传全集。
默认值取全集，保证未显式传参的调用方行为不变。

### 4.6 提示词：只加强纠正类的主动性

`_memorySection`（`agent_service.dart:1237`）当前的判据是"下次对话没有它，我会做得
更差"，并明写"不要给用户建档案"。这两句压低了主动性，但它们**当初是对的**——
在没有 dreaming 兜底时，放开主动性只会让噪声挤占零和的画像预算。

二期的调整是**有针对性的，不是整体放开**：

- **加强**：用户在对话中纠正助手做法时立即 `remember`。这类记忆 dreaming 永远
  拿不到——它发生在对话里，笔记里没有。这是在线模型相对 dreaming 的唯一优势场景。
- **不变**：文风、品味类不再要求模型在线判断，改由 dreaming 提供。在线模型看到的
  样本量太小，判断不如离线批量归纳可靠。
- **新增**：说明画像中的 `taste` / `voice` 由后台归纳产生，模型不应重复写入同类条目。

## 五、会话检索工具（独立小项）

新增只读工具 `session_search`，包一层已有的 `searchSessions()`
（`chat_session_service.dart:670`）。

- **职责边界**（三套检索必须互不重叠，否则模型会在来源之间反复横跳）：
  `explore_notes` 管用户写过什么，`recall` 管助手记下的长期结论，
  `session_search` 管"我们之前聊过什么"。
- 与 dreaming 无依赖，可独立实现与合入。

## 六、隐私与安全

- 全流程**端侧发起**，除既有 AI provider 调用外不新增任何外部传输目标。
- dreaming 的模型调用发往用户自己配置的 provider，与现有洞察/每日提示同一条链路，
  不引入新的数据出境路径。
- 归纳结果只存本地 `agent_memory.db`，沿用一期"不进备份、不跨设备"的现状。
- 沿用一期的不可信数据处理：笔记正文经 `untrusted_text` 包裹，只作证据不作指令。
- 写入画像的是**结构特征**而非笔记原文（见 4.4），降低私密内容被反复注入到
  每日提示这类高频触点的风险。
- 关闭长期记忆时，dreaming 整体不运行。

## 七、上线前置条件（硬性）

> dreaming 会显著增加记忆条目的产生速率，且全部为系统静默写入。
> **以下两项必须与 dreaming 同期交付，不接受"先上线后补"。**

1. **设置页的记忆管理列表**：可查看、可删除全部画像条目与近况切片。
   当前用户只能通过与助手对话来改记忆（研究文档待办第 5 条），在人工写入速率下
   尚可接受；一旦系统开始静默写入，这就变成了"看不见也改不掉"。
2. **来源可归因**：dreaming 写入的条目要能显示依据来自哪几篇笔记。

理由见 3.2。这两项不是锦上添花，是这个功能能不能被信任的分界线。

## 八、待办与已知缺口

- **记忆与历史会话的跨设备同步（待办，未排期）**：两者目前都是设备级本地数据
  （见 2.5），换机即失忆。难点是跨设备合并会产生互相矛盾的画像条目——一期已因此
  显式放弃。**dreaming 会加重这个问题**：两台设备各自归纳会产出两套不同的
  `voice` / `taste`。同步方案需要先解决"同 kind 单条"的冲突合并语义，
  建议在 dreaming 一期数据积累后单独立项。
- **近况切片 14 天 TTL** 与 **最低样本量 10 条**均为初值，需用实际数据校准。
- **接入 models.dev 能力表**（独立项）：为 dreaming 选便宜档模型需要 `cost` 字段，
  同时可替换 `AIProviderSettings.supportsThinking`（`ai_provider_settings.dart:47-104`）
  中约 60 行随模型迭代失效的正则推断。已核实其 `api.json` 提供
  `reasoning` / `tool_call` / `modalities` / `limit` / `cost` 字段。
  **注意**：完整 `api.json` 约 4.4 MB / 204 家 provider，不可整包内置，
  需按仓库已支持的 provider 过滤后生成常量表。
- **多模态输入**（独立项，未排期）：当前请求构造只发文本。语音输入本轮明确不做。

## 十、明确不做

- **不生成笔记**。dreaming 的产物只进记忆库，不写入用户的笔记流。
  向用户的笔记里插入 AI 生成的内容，是笔记应用最不该越的界。
- **不做情绪判断**，不记录心理状态推测。
- **不评价用户**，尤其不比较摘录品味与原创水平之间的落差（见 3.3）。
- **不做语音输入**（本轮明确排除）。
- **不新增用户可见的后台任务提示**（见 3.6）。
